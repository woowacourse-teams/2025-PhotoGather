# 자동 토큰 갱신 테스트 가이드

## 사전 준비사항

테스트 전 다음을 확인하세요:
1. 백엔드 `/api/admin/refresh` 엔드포인트가 구현되어 있음
2. 백엔드가 올바른 응답 형식을 반환함:
   ```json
   {
     "accessToken": "new_access_token",
     "refreshToken": "new_refresh_token"  // optional
   }
   ```
3. Admin user 계정이 존재함
4. 브라우저 DevTools가 열려 있음 (Console + Network 탭)

## 테스트 시나리오 1: 기본 토큰 갱신 (수동 토큰 만료)

### 목적
만료된 Access Token이 자동 갱신과 요청 재시도를 트리거하는지 확인

### 단계

1. **어드민 패널에 로그인**
   - 이동: `http://localhost:8080/admin/login`
   - 자격 증명 입력 및 로그인
   - `/admin/spaces`로 리다이렉트되어야 함

2. **브라우저 DevTools 열기**
   - F12 누르기 또는 우클릭 → 검사
   - **Console** 탭으로 이동
   - **Application** 탭 → Local Storage → `http://localhost:8080`으로 이동

3. **Access Token 수동으로 만료시키기**
   - 키 찾기: `admin_access_token`
   - 토큰 값 복사
   - https://jwt.io 로 이동
   - "Encoded" 섹션에 토큰 붙여넣기
   - "Decoded" 섹션에서 `exp` 필드 찾기
   - `exp`를 과거 타임스탬프로 변경 (예: `1000000000`)
   - jwt.io에서 새로 인코딩된 토큰 복사
   - localStorage의 `admin_access_token` 값을 만료된 토큰으로 교체

4. **API 요청 트리거**
   - Spaces 테이블에서 "Code" 컬럼 클릭
   - 또는 페이지 새로고침

5. **콘솔 출력 확인**
   ```
   [API] 401 Unauthorized 감지: /api/admin/spaces/{code}
   [API] Access Token 갱신 시도...
   [Auth] Access Token 갱신 시도 중...
   [Auth] Access Token이 성공적으로 갱신되었습니다.
   [API] Access Token 갱신 완료. 원래 요청 재시도: /api/admin/spaces/{code}
   ```

6. **Network 탭 확인**
   - 다음이 표시되어야 함:
     - 첫 번째 요청: `GET /api/admin/spaces/{code}` → 401
     - 갱신 요청: `POST /api/admin/refresh` → 200
     - 재시도 요청: `GET /api/admin/spaces/{code}` → 200

7. **localStorage 확인**
   - `admin_access_token`이 업데이트되었는지 확인 (다른 값)
   - 새 토큰은 미래의 만료 시간을 가져야 함

### 예상 결과
- 로그인 페이지로 리다이렉트 없이 페이지가 정상적으로 로드됨
- 모달이 열리며 스페이스 상세 정보가 표시됨
- 사용자에게 에러 메시지가 표시되지 않음

### 테스트 결과
- [ ] PASS: 페이지 로드됨, 모달 열림, 콘솔에 갱신 로그 표시
- [ ] FAIL: 로그인 페이지로 리다이렉트됨 / 에러 메시지 표시됨

## 테스트 시나리오 2: 동시 요청 (여러 동시 401 에러)

### 목적
401을 반환하는 여러 동시 API 요청이 refresh token API 호출을 단 1회만 트리거하는지 확인

### 단계

1. **어드민 패널에 로그인**
   - 이동: `http://localhost:8080/admin/login`
   - 로그인 성공

2. **Network 탭 열기**
   - DevTools → Network 탭 열기
   - "Fetch/XHR"로 필터링
   - "Preserve log" 옵션 활성화

3. **Access Token 만료시키기**
   - 테스트 시나리오 1의 단계를 따라 토큰을 수동으로 만료시킴

4. **여러 요청 동시에 트리거**
   - Spaces 페이지 새로고침 (F5)
   - 이는 여러 API 호출을 한 번에 트리거함

5. **Network 탭 확인**
   - `POST /api/admin/refresh` 요청이 몇 개 나타나는지 세기
   - **예상: 정확히 1개의 갱신 요청**
   - 여러 원래 요청들은 다음을 표시해야 함:
     - 첫 번째 시도: 401
     - 재시도: 200

6. **콘솔 출력 확인**
   ```
   [API] 401 Unauthorized 감지: /api/admin/spaces
   [API] Access Token 갱신 시도...
   [API] 401 Unauthorized 감지: /api/admin/spaces/{code}
   [API] Access Token 갱신 시도...
   [Auth] Access Token 갱신 시도 중...
   [Auth] Access Token이 성공적으로 갱신되었습니다.
   [API] Access Token 갱신 완료. 원래 요청 재시도: /api/admin/spaces
   [API] Access Token 갱신 완료. 원래 요청 재시도: /api/admin/spaces/{code}
   ```

### 예상 결과
- Network 탭에 `/api/admin/refresh` 호출이 단 1개만
- 모든 원래 요청이 재시도되고 200 OK로 성공
- 모든 데이터가 올바르게 로드됨

### 테스트 결과
- [ ] PASS: 갱신 요청 1개만, 모든 재시도 성공
- [ ] FAIL: 여러 갱신 요청 / 일부 요청 실패

## 테스트 시나리오 3: Refresh Token 만료

### 목적
만료된 Refresh Token이 자동 로그아웃과 로그인 페이지 리다이렉트를 발생시키는지 확인

### 단계

1. **어드민 패널에 로그인**
   - 이동: `http://localhost:8080/admin/login`
   - 로그인 성공

2. **두 토큰 모두 만료시키기**
   - DevTools → Application → Local Storage 열기
   - `admin_access_token` 만료 (테스트 시나리오 1 단계 따름)
   - `admin_refresh_token` 만료 (같은 단계 따름)

3. **API 요청 트리거**
   - Spaces 테이블의 아무 Code나 클릭
   - 또는 아무 어드민 페이지로 이동

4. **콘솔 출력 확인**
   ```
   [API] 401 Unauthorized 감지: /api/admin/spaces/{code}
   [API] Access Token 갱신 시도...
   [Auth] Access Token 갱신 시도 중...
   [Auth] Refresh Token이 만료되었습니다. 재로그인이 필요합니다.
   [API] Token 갱신 실패: Refresh token expired
   ```

5. **Network 탭 확인**
   - 첫 번째 요청: `GET /api/admin/spaces/{code}` → 401
   - 갱신 요청: `POST /api/admin/refresh` → 401
   - 재시도 없음 (갱신 실패했으므로)

6. **localStorage 확인**
   - 두 토큰 모두 삭제되어야 함 (빈 값 또는 제거됨)

### 예상 결과
- 사용자가 `/admin/login`으로 자동 리다이렉트됨
- localStorage 토큰이 삭제됨
- 무한 루프나 여러 리다이렉트 시도 없음

### 테스트 결과
- [ ] PASS: 로그인 페이지로 리다이렉트됨, 토큰 삭제됨
- [ ] FAIL: 루프에 갇힘 / 리다이렉트 안 됨 / 토큰 삭제 안 됨

## 테스트 시나리오 4: 무한 루프 방지

### 목적
refresh API가 401을 반환하면 시스템이 무한으로 재시도하지 않는지 확인

### 단계

1. **Refresh API를 401 반환하도록 모킹**
   - 옵션 A: 브라우저 확장으로 `/api/admin/refresh`를 가로채서 401 반환
   - 옵션 B: 백엔드를 일시적으로 수정하여 refresh 엔드포인트에서 401 반환
   - 옵션 C: DevTools의 네트워크 스로틀링/차단 사용

2. **로그인 및 Access Token 만료시키기**
   - 테스트 시나리오 1 단계 따름

3. **API 요청 트리거**
   - Spaces 테이블의 아무 Code나 클릭

4. **콘솔 출력 확인**
   - 다음이 표시되어야 함:
     - 갱신 시도: `[Auth] Access Token 갱신 시도 중...`
     - 갱신 실패: `[Auth] Refresh Token이 만료되었습니다.`
     - 무한 루프 로그 없음

5. **갱신 시도 횟수 세기**
   - Network 탭 열기
   - `POST /api/admin/refresh` 요청 개수 세기
   - **예상: 정확히 1회 시도**

### 예상 결과
- 단 1회만 갱신 시도 (무한 재시도 없음)
- 사용자가 로그인 페이지로 리다이렉트됨
- 브라우저 정지나 충돌 없음

### 테스트 결과
- [ ] PASS: 단일 갱신 시도, 로그인 페이지로 리다이렉트됨
- [ ] FAIL: 여러 갱신 시도 / 무한 루프

## 테스트 시나리오 5: 토큰 갱신 후 정상 작동

### 목적
자동 토큰 갱신 후 이후 API 호출이 추가 갱신 없이 정상 작동하는지 확인

### 단계

2. **갱신 완료 대기**
   - 콘솔에 표시 확인: `[Auth] Access Token이 성공적으로 갱신되었습니다.`

   - 페이지 간 이동
   - 테이블에서 여러 Code 클릭

   - 페이지 크기 변경

4. **Network 탭 확인**
   - 모든 요청이 즉시 200 OK를 반환해야 함

   - 추가 갱신 요청 없음

### 예상 결과
- 모든 후속 요청이 갱신 없이 성공

## 테스트 시나리오 6: 긴 세션 중 토큰 갱신

### 목적
현실적인 시나리오에서 자동 토큰 갱신 확인 (정상 사용 중 토큰 만료)

4. **끊김 없는 경험 확인**

   - 콘솔에 갱신 로그 표시
   - 사용자에게 에러나 로그인 페이지가 표시되지 않음

### 예상 결과
- 자동 토큰 갱신이 투명하게 발생
- 사용자가 중단 없이 작업 계속

## 일반적인 문제와 해결책

### 문제 1: 무한 리다이렉트 루프
**증상**: 페이지가 `/admin/login`으로 계속 리다이렉트됨

**가능한 원인**:
- Refresh Token API가 구현되지 않음
- Refresh Token API가 잘못된 응답 형식 반환
- localStorage가 비활성화됨

**해결책**:
- 백엔드 `/api/admin/refresh` 엔드포인트 확인
- Network 탭에서 응답 형식 확인
- 브라우저 설정에서 localStorage 활성화

### 문제 2: 여러 Refresh 요청
**증상**: Network 탭에 여러 `/api/admin/refresh` 호출 표시

**가능한 원인**:
- `tokenRefreshPromise` 캐시가 작동하지 않음
- JavaScript 실행 순서 문제

**해결책**:
- 디버그 로그 추가: `console.log('tokenRefreshPromise 존재?', !!tokenRefreshPromise)`
- 스크립트가 올바른 순서로 로드되는지 확인
- 중복 API.request() 호출 확인

### 문제 3: 갱신 후에도 401 지속
**증상**: 토큰 갱신 후에도 요청이 401로 실패

**가능한 원인**:
- 재시도 시 Authorization 헤더가 업데이트되지 않음
- 백엔드가 새 토큰을 인식하지 못함

**해결책**:
- Network 탭 → Request Headers에서 Authorization 헤더 확인
- 백엔드가 새 Access Token을 올바르게 검증하는지 확인
- 디버그 로그 추가: `console.log('재시도 헤더:', options.headers)`

## 자동화 테스트 (향후 개선사항)

다음을 사용한 자동화 테스트 고려:
- **Playwright/Cypress**: 브라우저 자동화를 사용한 E2E 테스팅
- **Jest**: `Auth` 및 `API` 객체에 대한 단위 테스트
- **Mock Service Worker (MSW)**: 백엔드 응답 모킹

예시 테스트 케이스:
```javascript
describe('토큰 갱신', () => {
  test('401 시 토큰 갱신 및 재시도해야 함', async () => {
```
